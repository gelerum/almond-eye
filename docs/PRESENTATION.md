# Almond Eye: успеваем ли мы по графику? — материалы для презентации

> Рабочий документ для питча на хакатоне ДГП Москвы. Цифры из раздела «Результаты» пересчитываются
> скриптами (`scripts/eval_detectors.py`, `scripts/seed_demo.py`) и обновляются по ходу работы.

---

## 1. Проблема (слайд 1)

- Контроль соответствия стройки календарному графику сейчас ручной: просмотр камер, звонки подрядчикам,
  субъективные оценки.
- На площадках уже стоят камеры, и на снимках видно, **какая техника работает и где**.
- Наша цель — по снимкам автоматически отвечать на главный вопрос руководителя проекта:
  **«Мы опаздываем или успеваем?»** Ответ даём по каждому этапу, с объяснением и фото-доказательством.

## 2. Идея решения (слайд 2)

**Этап работ узнаём не по одной машине, а по «почерку» — сочетанию техники и материалов в кадре.**

| Что видим в кадре | Что это значит |
|---|---|
| буровые установки + автобетоносмеситель | идёт устройство свай / «стены в грунте» |
| экскаватор + самосвалы (± погрузчик, бульдозер) | разработка котлована |
| экскаватор **без** самосвалов | риск снижения темпа вывоза грунта (пример из ТЗ) |
| башенный кран + арматура/опалубка + бетоносмеситель/бетононасос | фундаментная плита, подземная часть |
| башенный кран + растущий каркас, леса | монтаж надземной части |
| автокран + башенный кран без каркаса | монтаж / демонтаж башенного крана |
| каток + самосвал/бульдозер | дороги, благоустройство |

Одна машина неоднозначна: экскаватор бывает и на котловане, и на сетях, и на благоустройстве.
Их сочетание однозначно. Для каждого кадра система выдаёт ранжированный список этапов и объяснение:
«вижу экскаватор и 2 самосвала, нет буровых → разработка котлована, уверенность 0.82».

## 3. Как снимок связывается с графиком (слайд 3, схема)

```
Снимок камеры ──► Ансамбль детекторов ──► Техника + материалы (боксы, уверенность, какая модель)
   (дата съёмки)          │
                          ▼
            Методика «этап → почерк техники»  (backend/app/rules/stage_signatures.yaml)
                          │
                          ▼
            Наблюдаемые этапы на дату снимка  ─────┐
                                                   ▼
Календарный план (XLSX, этапы × месяцы) ──► Плановые этапы на дату ──► Сравнение план/факт
                                                                           │
                                                                           ▼
                                   Статус по этапам + общий вердикт + алерты с фото
```

Правила сравнения на дату D (по всем снимкам объекта не позже D):

| Ситуация | Вывод |
|---|---|
| Этап по плану должен быть закончен, но на снимках после `end` ещё виден его почерк | **Отстаём на N дней** (N = последнее наблюдение − плановое окончание) |
| Этап по плану должен идти, а видим только предыдущий этап | **Отстаём: старт задерживается на N дней** |
| Видим этап раньше планового начала | **Опережаем на N дней** |
| Этап идёт, но не хватает обязательной техники (экскаватор без самосвалов) | **Риск снижения темпа** |
| В кадре техника, не нужная ни одному текущему этапу | **Техника не по этапу** |
| Нет снимков за окно / низкая уверенность | **Нет данных** — явно, без домыслов |

Общий вердикт по объекту — худший статус по этапам критического пути с максимальной задержкой:
«Отстаём на 34 дня: разработка котлована затянулась (последнее наблюдение 25.06, план до 31.05)».

## 4. Архитектура (слайд 4)

```
┌────────────── Web UI (apps/web, HTML/JS) ──────────────┐
│ Статус объекта: вердикт, Гант план/факт, алерты с фото │
│ Загрузка плана XLSX и снимков (дата задаётся при загрузке)│
└───────────────────────────┬────────────────────────────┘
                            │ REST
┌───────────────────────────▼────────────────────────────┐
│ FastAPI (backend/app/main.py)                           │
│  • импорт плана XLSX (gantt_import)                     │
│  • приём снимков + фоновые задачи анализа               │
│  • /status?date= — вердикт и алерты                     │
├─────────────────────────────────────────────────────────┤
│ Домен: stage_inference (почерк → этап),                 │
│        progress (план/факт → отставание),               │
│        evaluation (обязательная / лишняя техника)       │
├─────────────────────────────────────────────────────────┤
│ Детекторы (services/detectors, GPU):                    │
│  SiteSense YOLO26-L │ Grounding DINO + CLIP-верификация │
│  YOLO11-seg материалы │ YOLO11 арматура │ hazard (люди) │
│  → слияние боксов (noisy-OR + конфликты классов)        │
├─────────────────────────────────────────────────────────┤
│ Хранилище: SQLite / PostgreSQL (versioned documents),   │
│ снимки по SHA-256; данные и веса — DVC (S3)             │
└─────────────────────────────────────────────────────────┘
```

Запуск: `docker compose up` (GPU через CDI, есть и CPU-режим).

## 5. Модели и почему именно они (слайд 5)

| Модель | Что даёт | Почему |
|---|---|---|
| **SiteSense YOLO26-L** (MIT) | экскаватор, самосвал, бульдозер, погрузчик, автокран, башенный кран, каток, бетоносмеситель | закрытый набор строительной техники; быстрая (≈0.07 с на кадр на RTX 3060); лучшая точность в нашем пилоте |
| **Grounding DINO base** (Apache-2.0) | буровые/сваебойные установки, гусеничные краны, бетононасосы, материалы | открытый словарь: классы, которых нет ни в одном открытом датасете техники |
| **CLIP ViT-L/14** (верификатор) | переклассификация кропов DINO | DINO хорошо находит «высокую стрелу», но путает буровую, гусеничный и автокран; CLIP по кропу различает |
| **YOLO11s-seg, дообучен на VT Structural Material** (CC0, 3817 фото) | доли бетона, стали, профнастила в кадре | признак стадии: бетонные конструкции и металлокаркас |
| **YOLO11s, дообучен на ConRebSeg** (CC BY 4.0, 2216 кадров) | открытая арматура | признак армирования; на наших кадрах ловит в основном арматурные каркасы свай, вклад небольшой (+1 п.п.) |
| Construction Hazard YOLO11n (AGPL-3.0) | люди и СИЗ | обзор сцены (люди в зоне работы техники) |

Слияние: боксы одного класса от разных моделей объединяются; уверенность считается как noisy-OR,
поэтому согласие двух моделей сильнее каждой по отдельности. Взаимоисключающие классы (автокран и
буровая на одной машине) разрешаются в пользу более уверенного. Пороги по классам подбираются на
нечётных кадрах, а качество меряется на чётных, то есть не на тех же кадрах.

Заменили SODA на ConRebSeg: официальная ссылка на SODA (SharePoint HKUST) удалена, осталась только Baidu Pan.

## 6. Данные (слайд 6)

- **100 снимков организатора** (`data/raw/dgp/images`, проверка SHA-256 через `scripts/setup_data.py`).
  При ручном просмотре выяснилось: это **ежемесячные фотоотчёты 10 реальных площадок**, дата вшита
  штампом в кадр.
  - 5 площадок с датированными сериями: A (апр 2023 – авг 2024, 16 кадров), B (янв–июн 2024, 27),
    C (окт 2023 – фев 2024, 13 с датой из 16), D (сен 2024 – фев 2025, 6), E (янв–мар 2026, 3 с датой из 4).
  - 5 площадок без дат или из 1–2 кадров (G, H, I, F, J): используются для проверки детекции.
- **Ручная разметка** `data/manifests/dgp_images.json`: площадка, дата, наличие каждого класса техники,
  наблюдаемый этап, ракурс (земля/высота).
  - Больше всего экскаваторов (66 кадров) и буровых установок (48).
  - Этапы: сваи (40), котлован (34), подземная часть (9), подготовка территории (8), фундамент (5), надземная часть (3).
- **Проверочный набор** построен так, как требует ТЗ: разные сезоны (снег, лето, осень), ракурсы
  (с земли и с высоты), освещённость, 12 классов техники.
- **Внешние датасеты:** VT Structural Material (CC0), ConRebSeg (CC BY 4.0), SiteSense (обучен автором на
  открытых строительных датасетах).

## 7. Календарный план (слайд 7)

- Образец организатора («календарный план.pdf», ЖК «Мичуринский») — пустой шаблон: этапы × месяцы.
- Мы сделали **свои планы в том же формате** (XLSX: строки — этапы, столбцы — месяцы, залитые ячейки —
  интервалы, плюс столбцы «Начало/Окончание» с точными датами) для каждой датированной площадки.
  Этапы берутся из шаблона и сводного перечня работ ЛТЦ.
- Планы специально построены под разные сценарии: объект в графике, объект с отставанием и объект с опережением.
  Так на демо видно, что система различает эти случаи.
- Импорт понимает и такой XLSX-Гант, и CSV-формат `stage_id;work_name;start;end`.

## 8. Демонстрация (слайд 8, живое демо)

1. Выбираем площадку B и дату 25.06.2024.
2. Видим вердикт: «Отстаём на 34 дня: разработка котлована не завершена в срок (последнее наблюдение
   25.06, план до 22.05)» и «Фундамент не начат».
   - Гант показывает полосы плана и точки наблюдений: цвет — распознанный этап, клик открывает снимок.
3. Открываем снимок-доказательство: рамки техники, распознанный этап и объяснение
   («вижу экскаваторы, нет буровых → котлован»).
   - Алерт из ТЗ «экскаватор без самосвалов» показываем в режиме эталонной разметки
     (`seed_demo.py --ground-truth`); на детекторах он подавлен, см. слайд 10.
4. Сдвигаем дату назад и видим, как менялся статус объекта.
5. Загружаем новый снимок, указываем дату и получаем пересчитанный вердикт за секунды.

## 9. Результаты (слайд 9)

Подробно: `docs/DETECTION_EVAL.md`. Метрика — есть ли класс в кадре (P / R). Пороги подбирались на
нечётных кадрах, качество мерили на чётных.

**Распознавание техники (ансамбль, отложенные кадры):**

| Класс | P / R | Чем достигнуто |
|---|---|---|
| экскаватор | 0.89 / 0.97 | SiteSense |
| буровая установка | **0.91 / 0.91** | DINO + CLIP-верификация (до верификации: 0.67 / 0.09) |
| башенный кран | 0.75 / 0.92 | SiteSense |
| гусеничный кран | 0.80 / 0.67 | DINO + CLIP |
| погрузчик | 0.71 / 0.71 | SiteSense |

**Определение этапа по «почерку» техники** (100 кадров): **71%** верно с первой попытки, 81% в двух лучших.
Потолок методики при идеальном распознавании техники — 74% / 84%.

**Вердикт «успеваем / отстаём» на реальных детекторах** (5 площадок):
- A и B точно совпали с эталоном: «отстаём на 25 дн.» и «отстаём на 34 дн.»;
- C: сроки определены верно;
- D и E ошиблись на пограничных кадрах.

**Скорость (RTX 3060):** полный ансамбль ≈3.3 с на кадр. Без Grounding DINO — ≈0.1 с на кадр.
Для камер со снимком раз в 15–60 минут это с большим запасом.

**Что дало больше всего:** CLIP-проверка кропов DINO (буровые R 0.09 → 0.91) и калибровка
уверенности проверенных классов (этап 47% → 70%); модель арматуры добавила ещё 1 п.п. (71%).

## 10. Честные ограничения (слайд 10)

- Присутствие техники ≠ выполнение работ: мы оцениваем **признаки** этапа, а не объёмы.
- Разметка 100 кадров сделана одним разметчиком по визуальному просмотру и не перепроверена вторым.
- Буровые установки, гусеничные и автокраны визуально похожи. Это самый трудный класс, поэтому
  добавлена CLIP-верификация, а алерт «нет обязательной техники» разрешён только для классов
  с проверенной точностью (`validated_classes`).
- Сегментатор материалов обучен на фото мостов. На его собственных данных mAP50 0.75, но на стройплощадках
  он почти ничего не находит и на точность этапа не повлиял. Это честный отрицательный результат:
  модель оставлена опциональной.
- Самосвалы распознаются с полнотой 0.75 всего на 8 примерах, поэтому класс не проверен. Алерт из ТЗ
  «экскаватор без самосвалов» работает на эталонной разметке, но на выходе детекторов пока подавлен:
  иначе каждый четвёртый кадр с самосвалами давал бы ложную тревогу.
- Хуже всего различаются фундамент и подземная часть (0/5 и 3/9): техника та же, что на котловане, и
  различить их можно только по материалам — арматуре, опалубке, бетону.
- Планы для демо-площадок составлены нами, реальных графиков этих объектов у нас нет.

## 11. Рекомендации по установке камер (слайд 11)

- **Высокая точка обзора (15–40 м)**, например на башенном кране или соседнем здании: весь котлован
  в кадре, техника не перекрывает друг друга. Наши данные: на кадрах с высоты видно больше машин.
- **Одна камера на зону работ** с фиксированным ракурсом: тогда зоны (полигоны) размечаются один раз.
- **Регулярные снимки** (каждые 15–60 мин в рабочее время), а не раз в месяц. Отставание измеряется
  с точностью до интервала между снимками.
- **Метка времени от камеры (EXIF/NTP)**, а не штамп в кадре.
- **Разрешение от 1920×1080**: буровые мачты и стрелы кранов тонкие, на малых разрешениях теряются.
- Не снимать против солнца; зимой нужен подогрев и очистка объектива.

## 12. Масштабирование (слайд 12)

- Новые типы техники: добавить класс в `Equipment`, фразу для Grounding DINO и строку в методике.
  Переобучение не нужно.
- Новые этапы: строка в `stage_signatures.yaml`. Методика открыта и проверяема, её можно править без программиста.
- Много площадок: воркер-очередь для анализа, PostgreSQL, S3 для снимков (DVC уже настроен).
- Потоковое видео (RTSP): брать кадры раз в N минут и трекать технику, чтобы считать машино-часы.
- Интеграция с ИАС/ЕГС ДГП: импорт графиков из XML/MS Project, экспорт алертов.
- Дообучение на своих данных: разметка кадров, где модели разошлись (active learning).

## 13. Команда и стек (слайд 13)

Python 3.12, FastAPI, SQLAlchemy (SQLite/PostgreSQL), PyTorch 2 + CUDA, Ultralytics, 🤗 Transformers,
DVC + S3, Docker Compose (GPU). Лицензии всех моделей и датасетов зафиксированы в `data/sources/`.
